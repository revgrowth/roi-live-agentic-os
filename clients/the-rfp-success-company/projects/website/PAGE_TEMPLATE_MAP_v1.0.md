# **Purpose ****&**** Scope**

This document answers two questions for every page on The RFP Success® Company website: which design template does it use, and when does that template get built? It sits alongside the sitemap (which defines what pages exist) and the Master Client Feedback Tracker (which defines the rules those pages must follow). Together the three documents govern the entire build.

### **Who uses this document**

- **Jason Spencer (ROI.LIVE) — **Confirms template assignment before every new creative brief. Updates when pages get added or templates split.

- **Raja (design) — **Sees the full template inventory, which templates exist, which are queued, and what each covers.

- **Copywriters — **Confirm which template a brief targets before drafting. Inheritance from parent templates locks voice, structure, and rules.

- **Claude / AI assistants — **Loaded before any creative brief draft so template inheritance is applied correctly.

### **How templates relate to pages**

One template serves many pages. The Individual Service Page template will power five pages in launch plus future additions. The Industry Vertical template powers 12. The Case Study template powers 18. Each template gets designed once, then every page inheriting from it uses the same structural spine, section order, schema, and inheritance rules — populated with page-specific copy and data.

A page assignment is not arbitrary. It comes from the page's job: does this page convert, route, explain, prove, capture, or legally cover? Each of those jobs has a template.

### **How to update this document**

- When a new page gets added to the sitemap, assign it a template here before the creative brief starts.

- When a template's status changes (queued → in progress → complete), update the status field in Section 1.

- When Raja finishes a template, mark it complete and log the reference implementation page.

- When a template splits into variants (e.g., Case Study — Wine tier vs. Champagne tier), document the variants here.

- Bump version on the cover after meaningful changes. Quarterly review at minimum.

# **Section 3 — Template Dependency Map**

Which templates must exist before other templates can be finalized. Dependencies flow from bottom to top — the Homepage template feeds every other template in the chain.

| **WHY DEPENDENCIES MATTER: **A service page that links to case studies can't finalize its proof section until the case study template exists (or the links go to dead ends). Respecting dependencies prevents rework. |
| --- |

### **Dependency Layers**

#### **Layer 1 — Foundation (no dependencies)**

- **T1 Homepage **— establishes the design system every other template inherits.

- **T16 Policy Page **— standalone. No inheritance from conversion architecture.

#### **Layer 2 — Direct Homepage Inheritance**

- **T2 Service Landing **— inherits full design system from Homepage.

- **T4 Case Study **— inherits cards, stat treatment, typography.

- **T8 Index / Hub **— inherits filter/card patterns.

- **T9 Author Bio **— inherits typography, stat blocks.

- **T11 Quiz **— inherits CTA styles, form treatments.

- **T12 Lead Capture **— inherits hero, form, CTA patterns.

- **T13 Contact **— inherits form styles.

- **T17 Utility / Error **— inherits nav, footer, error-state conventions.

#### **Layer 3 — Multi-Inheritance**

- **T3 Individual Service Page **— inherits from T2 (service architecture) + T4 (case study cards for proof sections) + T1 (stat treatments).

- **T5 Industry Vertical **— inherits from T2 (service architecture) + T4 (case study cards for industry proof) + T1.

- **T10 About / Team **— inherits from T9 (Author Bio) for credential treatment + T1.
